# 协作规则（维护者 × AI 助手）

> 源于 2026-10 开发实践，双方共同遵守。改动本文件需维护者确认。

## 1. 环境基线

| 项 | 约定 |
|---|---|
| 本地开发 | Windows，`http://localhost:5111`，Node ≥ 22.5（内置 node:sqlite），数据在 `./data` |
| NAS 部署 | 群晖，路径 `/volume1/docker/homeledger`，Container Manager/compose；无公网，外网走 ZeroTier |
| 远端仓库 | `origin` = github.com/yibohub/homeledger（SSH），`upstream` = Panda-995/homeledger |
| 网络现实 | github.com HTTPS 直连常被重置 → **git 网络操作一律走 SSH**；gh-proxy.com 推送需注册，不用；NAS 拉镜像走 `ghcr.milu.moe` 中转 |

## 2. Git 与发版

- **标签 = 发版**：打 tag / 推 tag **只在维护者明确要求时执行**（tag 会触发 CI 构建并发布 GHCR 镜像）。CI 构建、改包可见性、NAS 切镜像等后续动作逐项确认后才动
- 功能开发走 **分支 → PR → 独立审查 → 修复发现 → 合并**；main 不直接进未经审查的功能提交（纯文档小改除外）
- 提交信息风格：发版用 `vX.Y.Z: 要点`；过程提交用 `docs:` / `fix:` / `feat:` / `test:` 前缀，中文正文说明"为什么"
- 已推送的 main 历史不重写（建仓库当次的回退为一次性特例）

## 3. 每批功能的标准流程

1. 较大功能先讨论对齐：落 `docs/` 文档（如 `ai-roadmap.md`），列明开放问题，维护者确认后再动手
2. 实现 + 每个功能配 `test/verify-*.js` 回归套件，登记进 `test/run-all.js`
3. **全量回归 14 套件全绿**才算完成（本地 Windows 也要绿，CI 是 Linux）
4. 版本三件套同步更新：`package.json` + `src/lib/about.js` CHANGELOG + `README.md` 更新记录
5. PR + 独立审查（子代理，审查者视角与实现者分离）→ 修复全部 P1 再合并
6. 合并后按需打 tag 发版（见第 2 条）

## 4. 产品设计红线

详见 `docs/ai-roadmap.md` §2，摘要：

- 数字靠统计（SQL），语言靠模型——模型不做任何算术
- 写库靠确认；自动入库是例外且必须有撤销手段
- AI 产出的账户/分类必须可溯源：原文依据或习惯统计，标注如实（「按习惯推荐」「账本默认」）
- 确定性优先：本地统计能解决的不烧 token；无 AI Key 时功能有降级路径
- 数据自持：出网内容限于账单原文 + 名称清单 + 聚合值，不发完整流水

## 5. 操作纪律（AI 侧自戒，均来自实际踩坑）

- **严禁 taskkill 全部 node.exe**——会连用户的 5111 开发实例一起杀；只按端口/PID 精确清理
- 不直接修改用户真实账目数据（`data/homeledger.db`），只建议操作或经确认后代做
- 服务端代码改动后须重启 5111 实例（plain node 无 --watch），并告知用户
- 测试调试只用隔离 `DATA_DIR` 实例；临时 8099 实例用完即清——残留实例会让 run-all 的 healthz 探到旧数据，整套结果作废
- Windows 下删除数据目录前先停持有它的进程（文件锁会导致 rm 失败）

## 6. 沟通约定

- 中文沟通；结论先行，细节随后
- 面向公网/不可逆的动作（推 tag、发镜像、改 GHCR 可见性、改用户数据）逐项等待确认
- 用户会以截图/口述反馈实测问题——先查真实数据定位根因，再改代码，避免按猜测修
- **观察即登记**：过程中发现自己认为「应该调整或可以调整」的事项（UX 口径、小优化、验证时观察到的瑕疵），
  当场登记到 BOARD（待办/押后带触发条件）或提 issue 跟踪，不在对话里口头一提了之——口头观察会随会话丢失。
  **已经实现的、或当场顺手修掉的不登记**（修掉的在提交信息里说明即可），看板只跟未完成的事（2026-10-09 维护者定为规则并细化边界）
