## 1. 现状盘点

目前 AI 能力全部围绕「识别入账」一件事，入口三个：

| 入口 | 路由 | 行为 |
|---|---|---|
| AI 记账页 | `/api/ai/scan` → `/api/ai/confirm` | 截图 → 草稿 → 用户确认落库 |
| 文本识别 | `/api/ai/text` | 文字 → 草稿 → 确认落库 |
| AI 悬浮球 | `/api/ai/chat` | 截图/文字 → **识别后直接自动入库**（"发出去就记好"） |

技术底座（全部可复用，无需引入新依赖）：

- `src/lib/ai.js`：双引擎（OpenAI 兼容视觉模型 + 纯本地规则兜底）、`normalizeItem` 草稿规范化、分类/账户宽松匹配
- `src/lib/scheduler.js`：定时任务基建（每天 + 30 分钟轮询），已承载周期账单、预算预警、到期提醒
- 报表统计函数（`routes/reports.js`、`lib/charts.js`）：分类汇总、环比、预算执行率
- `src/lib/txn.js`：统一记账入口 `createTransaction`（含余额重算、审计）
- 悬浮球前端 `public/js/assistant.js`（约 200 行，原生 JS）

### 现状的三个缺口

1. **只会记，不会答**：问"这个月餐饮花了多少"，悬浮球只会把它当成一笔待记的账，无法查询账目
2. **没有记忆**：账户/分类识别不出来时留空（悬浮球则直接兜底到"账户列表第一个"），历史使用习惯完全没用上
3. **自动入库无后悔药**：悬浮球识别错即入库，用户事后需要手动找出来删

## 2. 设计原则（贯穿所有方案）

1. **数字靠统计，语言靠模型**——任何涉及金额、统计、对账的计算一律走 SQL/统计函数，大模型只负责意图理解与结果叙述，绝不让模型心算
2. **写库靠确认**——AI 产出草稿/建议，用户确认才落库；自动入库是例外，必须有撤销手段
3. **确定性优先**——能用本地统计解决的（习惯推荐、模式挖掘）不烧 token、不依赖模型；模型只在语言层增值
4. **无 Key 可降级**——所有功能在未配置 AI Key 时有明确降级路径（统计类功能本来就不需要 Key）
5. **数据自持**——发给外部模型的内容限定为：账单原文/截图 + 分类账户**名称**清单 + 聚合统计值，不发送完整流水

#### P1 习惯记忆：账户/分类智能推荐 ⭐ 优先级最高

**一句话**：AI 识别不出的字段，用你自己的记账历史来补——"以你的记法为准"。

**解决什么问题**

- 文字记账（"午饭 35"）天然无付款方式 → 账户留空/兜底错账户 → 每次手动选或事后改
- 悬浮球自动入库时账户兜底到 `accounts[0]`（当前即"支付宝"问题），错账直接进库

**方案**

在 `normalizeItem` 草稿规范化处加本地统计推荐，识别结果优先、统计推荐兜底：

```
推荐链：同分类最常用账户（近90天）
      → 同商户最常用账户
      → 全账本最常用账户
      → 保持现状（留空 / 现行兜底）
```

- 实现：账本内一个 `GROUP BY account_id` 统计（家庭数据量毫秒级），**零 token、无 Key 也可用**（规则引擎同样受益）
- 确认页/悬浮球结果上标注「按你的习惯推荐」，让用户知道哪些是猜的
- 分类同理可加"商户 → 分类"记忆（肯德基 → 餐饮/午餐），越用越准

**涉及**：`src/lib/ai.js`（统计函数 + normalizeItem 兜底）、`routes/ai.js`（返回推荐标记）、`views/ai.ejs` / `assistant.js`（标注）。
**工作量**：S（半天）。**风险**：低。**数据库**：无变更。

**待讨论**

- 时间窗取 90 天还是 180 天？是否给近期交易加权？
- 按账本统计（推荐）还是按用户跨账本统计？
- 悬浮球自动入库场景，推荐置信度低于阈值时要不要改为"确认制"？

#### P2 AI 对话查账（自然语言问答）⭐ ✅ v1.9.0 已落地

> 实现注记：`src/lib/ai-ask.js`（意图解析 → SQL 出数 → 叙述三段管线）。三个「待讨论」的落地决策：
> 记/答分流取**隐式意图分类**（低置信反问）；首版问法做全五类；模型交互用**纯 JSON 输出约定**（不依赖 function-calling）。

**一句话**：让悬浮球学会"答"——"这个月餐饮花了多少""上季度比这个季度多花多少""房贷扣了没"。

**解决什么问题**：查账目前必须到报表页翻筛选器，移动端尤其繁琐。

**方案**（两段式，数字不走模型）

1. **意图解析**（小 prompt）：模型把自然语言转成结构化查询意图 JSON
   `{ "range": "this_month", "category_path": "餐饮", "group_by": "category", "compare": "prev_period" }`
2. **SQL 出数**：意图映射到现有报表统计函数（复用 `reports.js`/`charts.js` 的分类汇总、环比、预算执行率）
3. **叙述**（小 prompt）：把统计结果 + 数字模板交给模型写成两三句人话；模型拿不到任何"自己算"的机会

- 路由：`/api/ai/chat` 扩展 or 新增 `/api/ai/ask`（先做意图分类：这问句是"记账"还是"查询"，避免误入库）
- 无 Key 降级：识别常见问法走规则模板（"X月花了多少"正则可覆盖大半真实问法），答"请配置 AI 使用完整问答"
- 权限：只读成员可问（查询类），与账本角色一致

**涉及**：`routes/ai.js`、`lib/ai.js`（意图 + 叙述 prompt）、`assistant.js`（对话 UI 区分记/答气泡）。
**工作量**：M（1–2 天，含意图分类的边界打磨）。**风险**：中（问法长尾，需要意图兜底话术）。

**待讨论**

- "记账 vs 查询"的分流：显式（UI 两个 Tab）还是隐式（意图分类）？倾向隐式 + 置信度低时反问
- 首版支持哪几类问法：单分类汇总 / 时间段对比 / Top 榜 / 预算执行 / 某商户流水？
- 是否引入 function-calling 规范（部分兼容接口支持不一），还是纯 JSON 输出约定（更普适，倾向后者）

#### P7 月末支出预测与超支预警（设计已定案 2026-10-10，开发中）

**一句话**："按目前节奏，本月将支出 ¥8,400，餐饮预算将超 ¥300。"

**解决什么问题**：预算预警（checkBudgets）只会告诉你"已经超了"——看到通知时钱已花出去；
月末预测把窗口提前：月中就能知道"照这个花法月底会超"，还来得及踩刹车。

**方案（纯统计零 token，无 AI Key 全功能可用）**

预测三分量，已发生 + 日历精算 + 节奏外推：

```
本月预测支出 = 已发生支出 + 未来已知扣费 + 日常节奏外推
  已发生支出   = 本月 1 日至今 type IN ('expense','fee') 的 amount_base_cents 合计
               （与预算预警、首页「本月支出」大数字同一口径，无第二套统计）
  未来已知扣费 = 订阅扣费：status IN ('active','trial')、auto_renew=1 且今天 < next_charge_at ≤ 月末
                 （auto_renew=0「仅提醒」与 none/fixed 一样只提醒不扣费；金额与 charge()
                 入账同口径 rate=1）
               + 周期账单：is_active=1 且 auto_post=1，从 next_run_at 用 advanceDate()
                 逐期 walk 到月末，items 中支出口径的金额合计（income 规则不计）
  日常节奏外推 = 日常日均 × 剩余天数
    日常已发生 = 已发生支出 − 本月已入账固定扣费（source IN ('subscription','recurring')）
    日常日均   = 日常已发生 ÷ 已过天数（今天日号；今天已计入已发生）
    剩余天数   = 当月天数 − 已过天数（不含今天，即明天到月末）
```

**为什么拆"固定扣费"再外推**：直接「当月日均 × 剩余天数 + 已知扣费」会把月初已扣的
房租/年费外推一遍再精算一遍（双计），且月初一笔大额固定支出就把日均拉爆、全月预测失真。
拆开后固定支出走日历精算（准确），日常消费走节奏外推（合理），两个估计互不污染。
手动记的固定支出（如手工记房租）识别不出也不必识别——它会留在"日常节奏"里被外推，
恰好符合"每月都有这笔"的直觉。

**不预测情形（enough:false，展示面静默跳过）**：已过天数 < 3（月初样本太少）；
日常已发生 = 0 且无未来已知扣费（无从谈节奏）。仅对 **monthly + trigger_type='expense'**
预算出预测——P7 名为"月末"预测，weekly/yearly/custom 周期与收入预算首版不做。
已超支的预算不再出"将超支"（既有 checkBudgets 超支通知已接管），但总口径预测照常算。

**触发与通知**：计算函数放新 `lib/forecast.js`（对齐 sub-mining.js 先例：纯计算库，
scheduler 与 routes 共用，scheduler.js 已 360 行不再加）。scheduler.runDaily 每天跑
`checkForecasts()`（纯 SQL 毫秒级，幂等），**仅当预测月末使用率 > 100%（将超出预算）才通知**——
预测值在预算页人人可见，通知只报坏消息；kind 'warn'，dedupe
`forecast:{budget.id}:{month}:over` 月内一条，链接 /budgets。与 checkBudgets 互补：
它管"已经超了"（danger），P7 管"按节奏会超"（warn，提前若干天）。

**展示面**：①预算页每个 monthly 预算行加「预计月末 ¥X」+ 超/余着色（planning.js
/budgets 已算 dailyAllowance/remainingDays，同点顺手）；②报表页总口径一句预测条；
③手机 Tab1 预算条下一行小字（dashboard minimal 分支 budgets 已在手）；④通知中心见上。
文案统一带口径标注「按本月日常节奏 + 已知扣费估算」，管理偏差预期。

**涉及**：新增 `lib/forecast.js` + `test/verify-forecast.js`（登记 run-all，14→15 套件）；
`scheduler.js`（checkForecasts 挂进 runDaily）；`routes/planning.js` /budgets、
`routes/dashboard.js` minimal 分支、`routes/reports.js` 传预测数据；三个视图小改。
**工作量**：M（1–1.5 天含测试）。**风险**：预测偏差预期管理（口径标注缓解）。

**口径说明**：全预测按 amount_base_cents 单币种（与预算预警一致；订阅扣费入账 rate=1），
不做额外汇率折算——多币种折算属全 App 既有口径，不在 P7 范围内另起炉灶。

**待讨论（2026-10-10 维护者定案：「按推荐」，已全部落决策）**

- ~~日常节奏口径~~ **已决策**：拆固定扣费再外推（备选「全口径日均」否决——月初大额会把预测拉爆）

### 联动提案：AI 能力解锁的体验重构

---

#### P10 手机极简模式（依赖 P1 / P2 / P3）✅ 阶段 1 v1.10.0 / 阶段 2 v1.11.0（待打 tag）

> 实现注记：三决策落地——①触屏（手机 UA）默认开，cookie `hl_simple` 显式覆盖（`/ui-mode` 切换，
> 任何设备可选，桌面永不自动开启）；②「更多」页按领域分组（记账/分析/资产与计划/数据/协作与系统），
> 不做按频率动态排序（布局漂移打断肌肉记忆）；③捕获区即悬浮球的全屏形态（极简下隐藏悬浮球，
> 捕获区走 /api/ai/text→confirm 先草稿后确认管线，缺账户草稿给账户下拉默认第一项）。
> 阶段 2（问账嵌入 Tab1）已落地：问账分流下沉到 /api/ai/text（与 /api/ai/chat 共用 tryAssistantQuery
> 前置分支）——问句出回答卡（m-answer），记账句维持先草稿后确认；捕获区解除可写权限包裹，
> 只读成员可问（拍单按钮按权限隐藏、主按钮变「提问」）；桌面 AI 页「文字快记」同分流。
> 不能直接改用 /api/ai/chat：其记账分支是自动入库（发出去就记好），会破坏捕获区的草稿确认语义。
> 已知接受的暴露面（PR #12 审查登记）：两个端点的查询分支先于写权限检查，只读成员可触发
> LLM 调用（parse+narrate 最多两次）且无会话级频控——与 v1.9.0 悬浮球同类的既有面，
> 家庭自托管场景接受；多成员日常使用或发现 token 异常消耗时再加每用户频控（BOARD 押后表跟踪）。

**一句话**：手机端从"22 页管理后台的响应式压缩"变成"记、答、看三件事的聚焦界面"。

**背景与前提**

当前移动端是全功能信息架构的平铺：22 个页面、完整表单、全部筛选器，复杂度来源不是页面多，而是**所有场景都按桌面管理后台的方式组织**。手机的真实场景只有两个高频动作——随手记一笔、瞄一眼账目；报表分析、预算配置、订阅管理都是低频管理动作。

关键判断：**简化能否成立取决于 AI 能否接住"记"**。如果记账仍要填 5–8 个字段的表单，简化界面只能靠藏功能（等于阉割）；P1 习惯记忆 + P3 语音 + 悬浮球落地后，手机记账变成「打开 → 说一句/拍一张 → 看一眼确认 → 完事」，简化才是聚焦而非删减。

**形态：三 Tab + 一条 AI 流**（信息架构重排，非重写；复用现有页面与组件）

```
┌─────────────────────────────┐
│ Tab1「记」                   │
│  本月支出/收入大数字+预算条    │ ← 复用统计函数
│  ┌───────────────────────┐  │
│  │  AI 捕获区             │  │ ← 🎤语音(P3) / 📷拍账单 / ⌨️文字
│  └───────────────────────┘  │     三合一入口
│  待确认草稿卡片流             │ ← P1 推荐预填，一键确认
│  最近 5 笔                   │
├─────────────────────────────┤
│ Tab2「明细」                 │ ← 复用 txn-list，点开即改
│  时间轴流水 + 搜索入口        │
├─────────────────────────────┤
│ Tab3「更多」                 │ ← 报表/日历/预算/订阅/账户/设置
│  按分组收纳（页面本身不动）    │    只重组入口，做好分组与搜索
└─────────────────────────────┘
```

- 设置加「手机极简模式」开关，触屏设备默认开，**桌面端零改动**
- 实现路径：SSR 内做（触屏判定 + 用户偏好 → 切 `layout-m` 布局 + 简化首页视图），不引前端框架
- 现有移动端响应式适配（v1.7.4 双视口巡检成果）不推翻，极简模式是在其上做减法

**分阶段**

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 阶段 1 | 三 Tab 重排 + AI 捕获首页 + 草稿卡片流 | P1（习惯推荐预填） |
| 阶段 2 | 「问账」对话嵌入 Tab1 | P2 对话查账 |

**涉及**：新增 `layout-m` 与简化首页视图、底部导航 IA 重组、`public/css/app.css` 增量。
**工作量**：M–L（阶段 1 约 2–3 天，阶段 2 约 1 天）。**风险**：中——最大风险是"功能发现性"（收纳太深找不到），靠「更多」页分组 + 搜索缓解；其次是双布局的长期维护成本（可控：管理页面维持现状，无双份业务逻辑）。

**待讨论**

- ~~极简模式触屏默认开还是显式选择？~~ **已决策（2026-10-09）**：触屏默认开 + cookie 显式覆盖（任何设备可选）——家庭场景里长辈是主要摩擦点，「手动开启」等于门槛；不满意一键回完整版
- ~~「更多」页的分组方式：按频率（常用置顶）还是按领域（记账/规划/管理）？~~ **已决策（2026-10-09）**：按领域分组——按频率排序会让布局随使用漂移，打断肌肉记忆；组内顺序首版固定
- ~~悬浮球与 Tab1 捕获区功能重叠，是否合并（倾向合并）？~~ **已决策（2026-10-09）**：合并——极简下隐藏悬浮球，捕获区即其全屏形态，且走先草稿后确认管线（更适合聚焦界面）

## 4. 明确不做（Non-Goals）

| 不做 | 原因 |
|---|---|
| 让模型对账/算总额/做任何算术 | 大模型数值不可靠，一律 SQL |
| 无确认的全自动批量入账 | 错账成本高于便捷收益；自动仅限悬浮球单条场景且有 P4 后悔药 |
| 自建/内置模型服务 | 破坏零依赖部署；坚持 OpenAI 兼容接口，模型选择权留给用户（GLM/通义/DeepSeek/Ollama） |
| 上传完整流水到外部模型 | 数据自持原则；出网内容限定为账单原文 + 名称清单 + 聚合值 |

```
择机:               P8 导入兜底 / P9 年度报告
```

**总量估算**：第一、二批合计约 3–4 人日；含 P10 全部落地约 13–17 人日。

## 6. 通用技术约束

- 全部走「设置 → AI 记账」的同一套 OpenAI 兼容配置，不新增任何配置项（除非功能必须有开关）
- 新增 prompt 一律要求"只输出 JSON"，复用 `normalizeItem` 的容错解析风格
- 统计类功能（P5/P6/P7/P9 的数字部分）不依赖 AI Key，无 Key 全功能可用
- 测试：每个功能在 `test/` 下补 verify 套件（对齐现有 8 套件风格：独立实例 + 干净数据目录），进 CI 门禁
