## 1. 现状盘点

目前 AI 能力全部围绕「识别入账」一件事，入口三个：

| 入口 | 路由 | 行为 |
|---|---|---|
| AI 记账页 | `/api/ai/scan` → `/api/ai/confirm` | 截图 → 草稿 → 用户确认落库 |
| 文本识别 | `/api/ai/text` | 文字 → 草稿 → 确认落库 |
| AI 悬浮球 | `/api/ai/chat` | 截图/文字 → **识别后直接自动入库**（"发出去就记好"） |

技术底座（全部可复用，无需引入新依赖）：

- `src/lib/ai.js`：双引擎（OpenAI 兼容视觉模型 + 纯本地规则兜底）、`normalizeItem` 草稿规范化、分类/账户宽松匹配
- `src/lib/scheduler.js`：定时任务基建（每天 + 30 分钟轮询），已承载周期账单、预算预警、到期提醒
- 报表统计函数（`routes/reports.js`、`lib/charts.js`）：分类汇总、环比、预算执行率
- `src/lib/txn.js`：统一记账入口 `createTransaction`（含余额重算、审计）
- 悬浮球前端 `public/js/assistant.js`（约 200 行，原生 JS）

### 现状的三个缺口

1. **只会记，不会答**：问"这个月餐饮花了多少"，悬浮球只会把它当成一笔待记的账，无法查询账目
2. **没有记忆**：账户/分类识别不出来时留空（悬浮球则直接兜底到"账户列表第一个"），历史使用习惯完全没用上
3. **自动入库无后悔药**：悬浮球识别错即入库，用户事后需要手动找出来删

## 2. 设计原则（贯穿所有方案）

1. **数字靠统计，语言靠模型**——任何涉及金额、统计、对账的计算一律走 SQL/统计函数，大模型只负责意图理解与结果叙述，绝不让模型心算
2. **写库靠确认**——AI 产出草稿/建议，用户确认才落库；自动入库是例外，必须有撤销手段
3. **确定性优先**——能用本地统计解决的（习惯推荐、模式挖掘）不烧 token、不依赖模型；模型只在语言层增值
4. **无 Key 可降级**——所有功能在未配置 AI Key 时有明确降级路径（统计类功能本来就不需要 Key）
5. **数据自持**——发给外部模型的内容限定为：账单原文/截图 + 分类账户**名称**清单 + 聚合统计值，不发送完整流水
6. **敏感分流**（2026-10-11 新增，维护者提议）——收入类关键词命中的文字记账不发送模型服务、走本地规则（默认开可关，见 `analyzeBill` 敏感预检与设置页「敏感记账走本地规则」）。词表从窄只拦方向无歧义的收入词：误拦的代价是规则链错向 + 悬浮球自动入库错数据，漏拦的代价只是照旧出网（现状）。截图路径与查账问答不受此管制（帮助文案如实注明）。

#### P1 习惯记忆：账户/分类智能推荐 ⭐ 优先级最高

**一句话**：AI 识别不出的字段，用你自己的记账历史来补——"以你的记法为准"。

**解决什么问题**

- 文字记账（"午饭 35"）天然无付款方式 → 账户留空/兜底错账户 → 每次手动选或事后改
- 悬浮球自动入库时账户兜底到 `accounts[0]`（当前即"支付宝"问题），错账直接进库

**方案**

在 `normalizeItem` 草稿规范化处加本地统计推荐，识别结果优先、统计推荐兜底：

```
推荐链：同分类最常用账户（近90天）
      → 同商户最常用账户
      → 全账本最常用账户
      → 保持现状（留空 / 现行兜底）
```

- 实现：账本内一个 `GROUP BY account_id` 统计（家庭数据量毫秒级），**零 token、无 Key 也可用**（规则引擎同样受益）
- 确认页/悬浮球结果上标注「按你的习惯推荐」，让用户知道哪些是猜的
- 分类同理可加"商户 → 分类"记忆（肯德基 → 餐饮/午餐），越用越准

**涉及**：`src/lib/ai.js`（统计函数 + normalizeItem 兜底）、`routes/ai.js`（返回推荐标记）、`views/ai.ejs` / `assistant.js`（标注）。
**工作量**：S（半天）。**风险**：低。**数据库**：无变更。

**待讨论**

- 时间窗取 90 天还是 180 天？是否给近期交易加权？
- 按账本统计（推荐）还是按用户跨账本统计？
- 悬浮球自动入库场景，推荐置信度低于阈值时要不要改为"确认制"？

#### P2 AI 对话查账（自然语言问答）⭐ ✅ v1.9.0 已落地

> 实现注记：`src/lib/ai-ask.js`（意图解析 → SQL 出数 → 叙述三段管线）。三个「待讨论」的落地决策：
> 记/答分流取**隐式意图分类**（低置信反问）；首版问法做全五类；模型交互用**纯 JSON 输出约定**（不依赖 function-calling）。

**一句话**：让悬浮球学会"答"——"这个月餐饮花了多少""上季度比这个季度多花多少""房贷扣了没"。

**解决什么问题**：查账目前必须到报表页翻筛选器，移动端尤其繁琐。

**方案**（两段式，数字不走模型）

1. **意图解析**（小 prompt）：模型把自然语言转成结构化查询意图 JSON
   `{ "range": "this_month", "category_path": "餐饮", "group_by": "category", "compare": "prev_period" }`
2. **SQL 出数**：意图映射到现有报表统计函数（复用 `reports.js`/`charts.js` 的分类汇总、环比、预算执行率）
3. **叙述**（小 prompt）：把统计结果 + 数字模板交给模型写成两三句人话；模型拿不到任何"自己算"的机会

- 路由：`/api/ai/chat` 扩展 or 新增 `/api/ai/ask`（先做意图分类：这问句是"记账"还是"查询"，避免误入库）
- 无 Key 降级：识别常见问法走规则模板（"X月花了多少"正则可覆盖大半真实问法），答"请配置 AI 使用完整问答"
- 权限：只读成员可问（查询类），与账本角色一致

**涉及**：`routes/ai.js`、`lib/ai.js`（意图 + 叙述 prompt）、`assistant.js`（对话 UI 区分记/答气泡）。
**工作量**：M（1–2 天，含意图分类的边界打磨）。**风险**：中（问法长尾，需要意图兜底话术）。

**待讨论**

- "记账 vs 查询"的分流：显式（UI 两个 Tab）还是隐式（意图分类）？倾向隐式 + 置信度低时反问
- 首版支持哪几类问法：单分类汇总 / 时间段对比 / Top 榜 / 预算执行 / 某商户流水？
- 是否引入 function-calling 规范（部分兼容接口支持不一），还是纯 JSON 输出约定（更普适，倾向后者）

#### P7 月末支出预测与超支预警（✅ v1.12.0 已落地）

**一句话**："按目前节奏，本月将支出 ¥8,400，餐饮预算将超 ¥300。"

**解决什么问题**：预算预警（checkBudgets）只会告诉你"已经超了"——看到通知时钱已花出去；
月末预测把窗口提前：月中就能知道"照这个花法月底会超"，还来得及踩刹车。

**方案（纯统计零 token，无 AI Key 全功能可用）**

预测三分量，已发生 + 日历精算 + 节奏外推：

```
本月预测支出 = 已发生支出 + 未来已知扣费 + 日常节奏外推
  已发生支出   = 本月 1 日至今 type IN ('expense','fee') 的 amount_base_cents 合计
               （与预算预警、首页「本月支出」大数字同一口径，无第二套统计）
  未来已知扣费 = 订阅扣费：status IN ('active','trial')、auto_renew=1 且今天 < next_charge_at ≤ 月末
                 （auto_renew=0「仅提醒」与 none/fixed 一样只提醒不扣费；金额与 charge()
                 入账同口径 rate=1）
               + 周期账单：is_active=1 且 auto_post=1，从 next_run_at 用 advanceDate()
                 逐期 walk 到月末，items 中支出口径的金额合计（income 规则不计）
  日常节奏外推 = 日常日均 × 剩余天数
    日常已发生 = 已发生支出 − 本月已入账固定扣费（source IN ('subscription','recurring')）
    日常日均   = 日常已发生 ÷ 已过天数（今天日号；今天已计入已发生）
    剩余天数   = 当月天数 − 已过天数（不含今天，即明天到月末）
```

**为什么拆"固定扣费"再外推**：直接「当月日均 × 剩余天数 + 已知扣费」会把月初已扣的
房租/年费外推一遍再精算一遍（双计），且月初一笔大额固定支出就把日均拉爆、全月预测失真。
拆开后固定支出走日历精算（准确），日常消费走节奏外推（合理），两个估计互不污染。
手动记的固定支出（如手工记房租）识别不出也不必识别——它会留在"日常节奏"里被外推，
恰好符合"每月都有这笔"的直觉。

**不预测情形（enough:false，展示面静默跳过）**：已过天数 < 3（月初样本太少）；
日常已发生 = 0 且无未来已知扣费（无从谈节奏）。仅对 **monthly + trigger_type='expense'**
预算出预测——P7 名为"月末"预测，weekly/yearly/custom 周期与收入预算首版不做。
已超支的预算不再出"将超支"（既有 checkBudgets 超支通知已接管），但总口径预测照常算。

**触发与通知**：计算函数放新 `lib/forecast.js`（对齐 sub-mining.js 先例：纯计算库，
scheduler 与 routes 共用，scheduler.js 已 360 行不再加）。scheduler.runDaily 每天跑
`checkForecasts()`（纯 SQL 毫秒级，幂等），**仅当预测月末使用率 > 100%（将超出预算）才通知**——
预测值在预算页人人可见，通知只报坏消息；kind 'warn'，dedupe
`forecast:{budget.id}:{month}:over` 月内一条，链接 /budgets。与 checkBudgets 互补：
它管"已经超了"（danger），P7 管"按节奏会超"（warn，提前若干天）。

**展示面**：①预算页每个 monthly 预算行加「预计月末 ¥X」+ 超/余着色（planning.js
/budgets 已算 dailyAllowance/remainingDays，同点顺手）；②报表页总口径一句预测条；
③手机 Tab1 预算条下一行小字（dashboard minimal 分支 budgets 已在手）；④通知中心见上。
文案统一带口径标注「按本月日常节奏 + 已知扣费估算」，管理偏差预期。

**涉及**：新增 `lib/forecast.js` + `test/verify-forecast.js`（登记 run-all，14→15 套件）；
`scheduler.js`（checkForecasts 挂进 runDaily）；`routes/planning.js` /budgets、
`routes/dashboard.js` minimal 分支、`routes/reports.js` 传预测数据；三个视图小改。
**工作量**：M（1–1.5 天含测试）。**风险**：预测偏差预期管理（口径标注缓解）。

不做额外汇率折算——多币种折算属全 App 既有口径，不在 P7 范围内另起炉灶。

##### P7 修订：临时大额不进节奏外推（2026-10-12 维护者认可方向，待排期）

**问题**（生产账实测）：手动/AI 记的临时大额支出全混在「日常节奏」里被线性外推——
老易账本 10 月上半月社保 ¥5,000 + 液化气 ¥990 等几笔，把日均从 ¥14.6 拉到 ¥574.4，
月预测 ¥7,170 被放大到 ¥17,806（2.5×）。原设计只拆了系统自动扣费（订阅/周期账单），
「手工记房租留在节奏里恰好符合直觉」的理由只覆盖*每月都有的*手动固定支出，覆盖不了*一次性*大额。

**分层方案（维护者已认可，K 值/下限等参数实现时标定）**：

1. **v1 阈值剔除（冷启动可用）**：节奏外推分子 = 已发生 − 系统固定扣费 − 临时大额单笔；
   大额判定 = 单笔 ≥ K×本月单笔金额中位数（中位数对大额自身免疫；生产数据 K=8 时
   老易账本阈值 ¥74，恰好剔 5 笔大额、留 ¥30 车辆维修在节奏），加绝对下限兜底小样本。
   防误伤：本月内同分类已重复 ≥2 次的大额不再剔除（每周加油的家庭它就是节奏）。
   剔除项仍计入「已发生」总额（沉没成本），只是不进外推；预测条文案加
   「已剔除临时大额 N 笔 ¥X」做口径标注。
2. **周期账单登记（未发生的算准）**：已知节奏的周期大额手动登记周期账单——
   **季付 = monthly + interval_n=3，advanceDate/knownFutureCents 已原生支持**，
   走日历精算零统计误差；已知扣费口径不变。
3. **v2 周期性定额收支挖掘（随数据成长）**：扩展 sub-mining.js（P5）做自动发现 →
   建议卡片 → 用户一键登记，只建议绝不自动建（P5 同哲学）。三个坑：MIN_RUN=3
   使季付需 9 个月流水才成链；分组键需从「商户」扩展「分类+金额相近」（房租常无商户名）；
   ±3 天间隔容差对手工记房租太窄（Q1→Q2 漂移 40 天即断链），需按日号+月数重设计消歧。
   押一付三/涨租由金额 ±10% 断链天然切成两段，longestChain 可直接对付。

**泛化口径**：判据不是「房租」分类，而是三特征——**定期（gap 落容差区）+ 定额（±10%）+
大额（相对中位数）**，方向无关（收入侧同算法：工资/房租收入/利息/分红；支出侧：
房贷/学费/保险/物业/取暖）。分类只做分组键候选，不做白名单（白名单兜不住 AI 误归类——
生产库 ¥5,000 社保被记进「其他」即活例）。大额但非周期的（装修/住院/旅行/份子）归 v1 阈值管。
**边界**：P7 仍只预测支出（收入不出预测），收入侧挖掘的归宿是登记收入周期账单，
服务未来净结余/现金流视图与问账口径。

**涉及**：`lib/forecast.js`（节奏分子剔除）+ `test/verify-forecast.js` 断言扩展 +
预测三视图文案；v2 另起批次动 `lib/sub-mining.js`。v1 工作量 S–M（半天–1 天含测试）。

#### P11 消费归属人提取（✅ PR #26 已合并待发版，2026-10-11）

**一句话**：记账时顺带识别「这笔钱为谁花的」——「口腔医院 老妈看牙齿」自动标上「老妈」，越记越懂家里每个人。

**为什么**（生产库观察 2026-10-11）：27 笔全 AI 记账，8 条备注里 4 条带家人（老爸/老妈/红霞），全散落在 merchant/note 自由文本。现有两套「成员」都接不住归属人：账本成员=注册用户（权限维度，长辈不会注册账号）、拆分成员=splits 自由文本（AA 分摊维度，从未用过）——缺的是独立的「消费归属人」标签。统计「谁的花了多少」目前只能翻备注。

**方案**（与 P1 习惯记忆同族：统计推荐 + 模型提取 + 确认落库）

1. **提取**：提示词输出端增加 `for_member` 字段（0~1 个归属人称呼，首版单归属人）；下发「家庭成员」名单 + 商户→归属人习惯摘要（「口腔医院→老妈」），模型从名单选或给新称呼
2. **臆造核验**：与账户同规则——文本记账时归属人称呼须在原文出现，否则丢弃（防模型编人名）；截图不受限
3. **落库**：transactions 新列 `owner_label TEXT`（自由文本，账本内归一：去空格/全半角统一）；草稿卡加归属人下拉（常用名单 + 可新建，确认制，不做无确认落库）
4. **习惯**：merchant→owner_label 统计（同款 90 天窗 / ≥2 次成习惯）进推荐链与提示词——「口腔医院」高频跟着「老妈」后自动带出
5. **消费端**：流水筛选 + 统计页新增「归属人」维度（谁的花了多少）；导出 CSV 加列（沿用 type_key 机读思路）
6. **边界**：归属人（为谁花）≠ 拆分成员（谁摊多少）≠ 账本成员（谁登录），三者互不替代，统计页可交叉

**定案（2026-10-11，四项待讨论均按推荐执行，随第五批落地）**

- 名单来源：设置手动维护（成员页「家庭成员（归属人）」，requireLedgerManage）+ 流水 distinct 自动沉淀混合——冷启动可控，见 `familyMembers()`；
- 存储选型：新列 `transactions.owner_label TEXT`（查询/筛选/导出干净），未复用 tags；
- 提示词防混淆：「账本成员」改称「记账用户（登录账号）」，归属人名单称「消费归属人候选」，for_member 只从后者选；
- 统计首版单维（归属人消费卡），「归属人 × 记账人」交叉留待共享账本场景。

**涉及**：`db.js`（新列迁移）、`lib/ai.js`（提示词 + normalizeItem + 归属人习惯）、`routes/ai.js`、草稿卡视图（桌面/极简）、流水筛选与统计页、导出列、`test/verify-ai-habit.js` 扩展。
**工作量**：M（1–1.5 天含测试）。**风险**：低（确认制 + 臆造核验）；无 Key 降级＝规则匹配名单称呼即填。

#### P12 习惯反馈闭环（✅ PR #27 已合并待发版，2026-10-11）

**一句话**：你把推荐改掉的那一下，就是最有价值的训练信号——现在统计不知道「推荐错了」，学错的习惯永远不退火。

**详设（2026-10-11 补齐，随第六批落地）**

1. **信号采集**：草稿确认（`/api/ai/confirm`）时对比「识别时的推荐快照」与最终值。快照由前端在应用用户编辑**之前**写入 `rec_snapshot{category_id, account_id, owner_label, type}`（m.js 展开草稿时、app.js 提交时按卡片 `data-i` 索引回取）；旧缓存 JS 不带快照则自然跳过（优雅降级）。只有「推荐过且有值」的字段被改才记负反馈（没推荐不算改，避免把「其他兜底被换成真分类」当惩罚）；清空/换掉都算改。类型被改（支出↔收入）时分类/账户跨 kind 比对无意义，只比归属人（与类型无关）。
2. **存储**：新表 `habit_feedback(ledger_id, merchant, field∈{category,account,owner}, recommended, confirmed, created_at)`，索引 (ledger_id, merchant, field)。写入时顺手清理 180 天前的旧行（反馈只在 90 天习惯窗内起作用，双窗防膨胀）。
3. **加权**：习惯统计一律 `weight = COUNT(*) − 2 × 负反馈数`——habitCategoryId（商户→分类）、habitOwnerId（商户→归属人）、habitAccountId 的商户维度，以及 buildHabitSummary 的商户→分类/归属人提示词摘要（分类→账户维度无负反馈归属，不加权）。分类/账户映射 weight<1 出局、归属人维持 ≥2 门槛：被改一次即把仅有的 2 次正例扣穿，学错的模式立即退火；90 天后负反馈滑出窗口自然复活（若期间正例还在涨）。
4. **P13 联动**：改掉「词表推荐」的分类时，对应词表条目 penalty+2（有效分 = hits − penalty，**跨 sediment 重估保留**——新流水刷新 hits 不抹掉教训），有效分扣穿即失效（dismissed），不再自动复活——词表只收「极稳」映射，活的部分交给习惯统计。
5. **边界**：悬浮球/对话自动入库（无人工评审时点）与确认后到流水页的后续编辑不产生反馈（前者没有比对时刻、后者跨页面归因复杂，先不做）；快照为客户端提供，仅影响本账本推荐质量，无安全面。纯统计零 token，无 Key 的规则引擎路径同样生效。

**涉及**：db.js（habit_feedback 表）、lib/ai.js（习惯加权 + recordDraftFeedback）、routes/ai.js（confirm 比对）、m.js/app.js（快照）、verify-ai-habit 扩展。

#### P13 个人动态词表（✅ PR #27 已合并待发版，2026-10-11）

**一句话**：系统关键词表是全体用户的，你的词表应该只属于你——「年册→集邮」「液化气→居家」。

**详设（2026-10-11 补齐，随第六批落地）**

1. **沉淀**：`settings['dict.categories.<ledgerId>']` JSON 数组，条目 `{kw, kind, category_id, hits, updated_at, dismissed}`。触发点 = 手动记一笔与 AI 草稿确认（用户有意识选过分类的时刻）；触发时重估该商户全历史（expense/income、分类未归档）：总笔数 ≥3 且主分类占比 ≥80% 才入表（「稳定映射」）。导入与开放 API 不触发（分类非本用户此刻的选择），但其流水计入统计基数。
2. **匹配**：normalizeItem 兜底链新序——规则引擎给出的分类名（出自系统关键词表，`engine:'rule'` 可辨）视为统计猜测，**个人词表优先于它**（先商户全等、再对「商户+备注+分类名」包含匹配，与系统表同口径；kind 过滤、分类已归档跳过）；大模型读账单明确给出的分类名仍是识别结果，优先于词表。其后依次：系统关键词表 → 习惯统计 → 「其他」。命中即预选并带「按习惯推荐」标记。
3. **可解释 / 可遗忘**：设置页 AI 区新卡「个人词表」逐条展示（商户→分类、笔数为扣除反馈罚分后的有效值、更新时间）+ 逐条删除（requireLedgerManage，对齐家庭名单管理权限；只读成员可看不可删）；删除置 dismissed=1 永不自动复活（防反复沉淀骚扰）；生效条目上限 200、已删条目保留上限 50（超出裁最旧）。
4. **误映射自愈**：P12 反馈扣穿（hits−2<1）自动失效；用户删词表后兜底链自然落回系统表/习惯/「其他」，不会卡死错误分类。纯统计零 token；词表内容（商户名+分类名）属既有出网白名单内，且本方案只走代码通道不进提示词（提示词通道已有 buildHabitSummary 商户→分类摘要覆盖）。

**涉及**：lib/dict.js（新）、lib/ai.js（兜底链）、routes/transactions.js + routes/ai.js（沉淀触发）、admin.js + settings.ejs（管理卡）、verify-ai-habit 扩展。

#### P14 few-shot 自适配（✅ 已关闭 2026-10-11，评估定案）

**一句话**：把你最近确认的几笔作为示例注入提示词，模型层面「记住你」。

**方案**：按相似度（同商户/同分类优先）取 2–3 条历史确认样本进 prompt。**与设计原则 5 有张力**：few-shot 样本接近「完整流水」，超出「账单原文 + 名称清单 + 聚合值」的出网边界——默认关 + 设置开关 + 样本脱敏（只带名称与分类，不带金额日期）可作为折中，需维护者拍板后再立项。
**工作量**：M。**风险**：中（出网边界）。

**定案（2026-10-11，维护者同意）**：关闭，不实施。

- 脱敏折中无增量价值：样本只剩「商户→分类」映射，与 P13 个人词表（代码通道、兜底链最优先）+ buildHabitSummary 商户→分类摘要（提示词通道）+ P12 反馈纠错三重覆盖重复；few-shot 真正的差异化价值（备注风格模仿、模糊词原文消歧）恰是脱敏裁掉的部分
- 完整版（历史原文出网）风险性质与现状重叠——账单原文每次识别本就整段出网，按 API Key 纵向累积画像的风险已存在，2~3 条样本只是密度略增；但「不发完整流水」是开源项目对所有部署者的对外承诺，不为边际增益修订
- **重开条件**：识别模型换成本地推理（`isLocalUrl`，如 Ollama）时，完整流水出网等于不出网，全量 few-shot 可零隐私代价开启（顺带可加「本地模型豁免」口径）；或维护者未来明确修订出网承诺

> 前置分支）——问句出回答卡（m-answer），记账句维持先草稿后确认；捕获区解除可写权限包裹，
> 只读成员可问（拍单按钮按权限隐藏、主按钮变「提问」）；桌面 AI 页「文字快记」同分流。
> 不能直接改用 /api/ai/chat：其记账分支是自动入库（发出去就记好），会破坏捕获区的草稿确认语义。
> 已知接受的暴露面（PR #12 审查登记）：两个端点的查询分支先于写权限检查，只读成员可触发
> LLM 调用（parse+narrate 最多两次）且无会话级频控——与 v1.9.0 悬浮球同类的既有面，
> 家庭自托管场景接受；多成员日常使用或发现 token 异常消耗时再加每用户频控（BOARD 押后表跟踪）。

**一句话**：手机端从"22 页管理后台的响应式压缩"变成"记、答、看三件事的聚焦界面"。

**背景与前提**

当前移动端是全功能信息架构的平铺：22 个页面、完整表单、全部筛选器，复杂度来源不是页面多，而是**所有场景都按桌面管理后台的方式组织**。手机的真实场景只有两个高频动作——随手记一笔、瞄一眼账目；报表分析、预算配置、订阅管理都是低频管理动作。

关键判断：**简化能否成立取决于 AI 能否接住"记"**。如果记账仍要填 5–8 个字段的表单，简化界面只能靠藏功能（等于阉割）；P1 习惯记忆 + P3 语音 + 悬浮球落地后，手机记账变成「打开 → 说一句/拍一张 → 看一眼确认 → 完事」，简化才是聚焦而非删减。

**形态：三 Tab + 一条 AI 流**（信息架构重排，非重写；复用现有页面与组件）

```
┌─────────────────────────────┐
│ Tab1「记」                   │
│  本月支出/收入大数字+预算条    │ ← 复用统计函数
│  ┌───────────────────────┐  │
│  │  AI 捕获区             │  │ ← 🎤语音(P3) / 📷拍账单 / ⌨️文字
│  └───────────────────────┘  │     三合一入口
│  待确认草稿卡片流             │ ← P1 推荐预填，一键确认
│  最近 5 笔                   │
├─────────────────────────────┤
│ Tab2「明细」                 │ ← 复用 txn-list，点开即改
│  时间轴流水 + 搜索入口        │
├─────────────────────────────┤
│ Tab3「更多」                 │ ← 报表/日历/预算/订阅/账户/设置
│  按分组收纳（页面本身不动）    │    只重组入口，做好分组与搜索
└─────────────────────────────┘
```

- 设置加「手机极简模式」开关，触屏设备默认开，**桌面端零改动**
- 实现路径：SSR 内做（触屏判定 + 用户偏好 → 切 `layout-m` 布局 + 简化首页视图），不引前端框架
- 现有移动端响应式适配（v1.7.4 双视口巡检成果）不推翻，极简模式是在其上做减法

**分阶段**

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 阶段 1 | 三 Tab 重排 + AI 捕获首页 + 草稿卡片流 | P1（习惯推荐预填） |
| 阶段 2 | 「问账」对话嵌入 Tab1 | P2 对话查账 |

**涉及**：新增 `layout-m` 与简化首页视图、底部导航 IA 重组、`public/css/app.css` 增量。
**工作量**：M–L（阶段 1 约 2–3 天，阶段 2 约 1 天）。**风险**：中——最大风险是"功能发现性"（收纳太深找不到），靠「更多」页分组 + 搜索缓解；其次是双布局的长期维护成本（可控：管理页面维持现状，无双份业务逻辑）。

**待讨论**

- ~~极简模式触屏默认开还是显式选择？~~ **已决策（2026-10-09）**：触屏默认开 + cookie 显式覆盖（任何设备可选）——家庭场景里长辈是主要摩擦点，「手动开启」等于门槛；不满意一键回完整版
- ~~「更多」页的分组方式：按频率（常用置顶）还是按领域（记账/规划/管理）？~~ **已决策（2026-10-09）**：按领域分组——按频率排序会让布局随使用漂移，打断肌肉记忆；组内顺序首版固定
- ~~悬浮球与 Tab1 捕获区功能重叠，是否合并（倾向合并）？~~ **已决策（2026-10-09）**：合并——极简下隐藏悬浮球，捕获区即其全屏形态，且走先草稿后确认管线（更适合聚焦界面）

## 4. 明确不做（Non-Goals）

| 不做 | 原因 |
|---|---|
| 让模型对账/算总额/做任何算术 | 大模型数值不可靠，一律 SQL |
| 无确认的全自动批量入账 | 错账成本高于便捷收益；自动仅限悬浮球单条场景且有 P4 后悔药 |
| 自建/内置模型服务 | 破坏零依赖部署；坚持 OpenAI 兼容接口，模型选择权留给用户（GLM/通义/DeepSeek/Ollama） |
| 上传完整流水到外部模型 | 数据自持原则；出网内容限定为账单原文 + 名称清单 + 聚合值 |
