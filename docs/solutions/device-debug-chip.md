# 真机前端疑难：诊断页 + 调试浮窗方法论（docs/solutions/device-debug-chip.md）

> 现象 → 方法 → 本项目现成工具。源自键盘避让的华为 ArkWeb 三轮排查（2026-10-10，
> 根因见 [deploy-nas.md](deploy-nas.md) 坑二），维护者确认有效并要求沉淀为常驻调试方法。

## 适用场景

前端行为**只在真机上异常**（桌面浏览器正常 / DevTools 模拟不出来或模拟不准）：
视口与软键盘、手势与缩放、内核私有行为、时序竞态。这类问题的共同困境是——
你看不到用户设备上的内部状态，只能看到「坏了」的结果，来回猜的沟通成本极高。

## 方法：把内部状态搬到屏幕上，让用户替你看一眼

四步，核心思想是**让设备自己交出证据**，而不是靠猜：

1. **先排除代码回归**：`git diff` 对比「好坏两个版本」，确认涉事代码零差异后，
   立刻转向「环境差异 + 状态时序」假设——不要再盯着改动本身（本轮动画改动
   被冤枉了三轮）。
2. **诊断页**：一个无鉴权静态 HTML（本项目 `/static/kb-diag.html`），实时显示
   内部数值（视口高度/缩放/指针类型）+ 事件日志（时间戳 + 数值快照）。发给用户
   一个 URL，手机打开截图——内核的真实行为一次到手，省掉 N 轮「你试试这样」。
3. **调试浮窗**：`localStorage` 门控的小浮窗，钉在页面角落实时刷新内部状态
   （本项目 m.js 的 `kb_debug` 开关，诊断页一键切换）。关键设计：
   - **localStorage 而非 URL 参数**——跨页面跟随，用户能走完整的多页复现路径
     （「记 → AI 记账 → 回记」哪一页坏一目了然），也不打扰正常使用；
   - `pointer-events: none` + 小字号半透明——不挡操作、无交互面；
   - 只显示数字不显示业务数据——无鉴权暴露面可接受。
4. **数值定根因**：让用户在坏的那一屏截图浮窗。本轮真机截图 `h=308 base=308
   open=0` 一眼锁定「基准高度学成了键盘态高度」——三轮排查的终局就靠这一个数字。

## 本项目现成工具（保留为常驻诊断设施）

| 工具 | 位置 | 开关 | 用途 |
|---|---|---|---|
| 诊断页 | `public/kb-diag.html` → `/static/kb-diag.html` | 直开即用 | 视口/事件流总览，一键开关浮窗 |
| 调试浮窗 | `m.js` 键盘适配 IIFE 内（`localStorage.kb_debug === '1'`） | 诊断页按钮 | 每个极简页面右上角实时 `path/h/base/open/scale` |

复用步骤：手机开诊断页 → 点「开启调试浮窗」→ 走复现路径 → 坏的那屏截图。
排查视口/键盘之外的问题时，照这两个文件的写法另起一份、换成要观察的状态即可
（模式不变：**localStorage 门控 + textContent 渲染 + 300ms 刷新**）。

## 经验教训

- **这类浮窗应该在写第一版交互时就埋上**（十几行、关着零开销）——真机行为
  与桌面不一致是常态，等坏了再补、再发版、再让用户升级，一轮就是半天。
- 「修复后时好时坏」大概率是**状态时序污染**（本轮：带键盘载入把基准学歪），
  不是新改动引入的回归——先 diff 排除，再上诊断工具。
- ArkWeb 等国产内核的视口行为见 [deploy-nas.md](deploy-nas.md) 坑二备查
  （scale 常态 0.96 且页面间漂移、键盘高度爆发式动画、事件不可依赖 → 轮询兜底）。
